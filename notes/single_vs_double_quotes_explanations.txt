## The Core Idea (One Sentence)

> **Quotes control whether the shell is allowed to *interpret* what’s inside.**

* **Single quotes `'...'` → “literal mode”** (shell does *nothing* inside)
* **Double quotes `"..."` → “expand but don’t split” mode**

---

## What the Shell Normally Does (Without Quotes)

When you type:

```bash
echo $USER *.c
```

The shell:

1. Sees `$USER` → **variable expansion**
2. Sees `*.c` → **wildcard (glob) expansion**
3. Splits on spaces

Example result:

```bash
echo dena main.c utils.c
```

---

## Single Quotes `'...'` — *Nothing Is Special*

**Rule:**

> Inside single quotes, **EVERY character is literal**.

The shell does **NO**:

* Variable expansion
* Wildcard expansion
* Backslash escapes
* Special meaning for `$`, `*`, `?`, `\`

### Examples

```bash
echo '$USER'
```

Output:

```text
$USER
```

Not your username — literally `$USER`.

```bash
echo '*.c'
```

Output:

```text
*.c
```

No file matching happens.

```bash
echo 'hello    world'
```

Output:

```text
hello    world
```

Spaces are preserved exactly.

### Think of single quotes as:

> **“Put this text into the token exactly as written.”**

---

## Double Quotes `"..."` — *Expand, But Stay Together*

**Rule:**

> Inside double quotes, the shell **does expansion**, but **does NOT split words**.

The shell **DOES**:

* `$VAR` expansion
* `$?`, `$$`, etc.

The shell **DOES NOT**:

* Split on spaces
* Perform wildcard expansion (`*` stays `*`)

---

### Examples

```bash
echo "$USER"
```

Output:

```text
dena
```

Variable expanded ✔️

```bash
echo "$USER is logged in"
```

Output:

```text
dena is logged in
```

Spaces stay inside one argument ✔️

```bash
echo "*.c"
```

Output:

```text
*.c
```

No glob expansion ❌

---

## Side-by-Side Comparison

| Input         | Result                                |
| ------------- | ------------------------------------- |
| `'$USER'`     | `$USER`                               |
| `"$USER"`     | `dena`                                |
| `'$HOME/*.c'` | `$HOME/*.c`                           |
| `"$HOME/*.c"` | `/home/dena/*.c`                      |
| `$HOME/*.c`   | `/home/dena/main.c /home/dena/util.c` |

---

## Why This Matters for Your Lexer / Minishell

During **tokenization**, quotes:

1. **Group characters into ONE token**
2. **Mark how expansion should behave later**

Example:

```bash
echo "hello $USER"
```

Your lexer might produce:

```
WORD("echo")
WORD("hello $USER", quote=DOUBLE)
```

Then during **expansion stage**:

* DOUBLE → expand `$USER`
* SINGLE → do nothing

### Single Quotes:

> 🧊 **Frozen text**
> “Shell, don’t touch this.”

### Double Quotes:

> 🧪 **Evaluate, but don’t break apart**

## One Tricky Edge Case (Worth Knowing)

You **cannot** put a single quote inside single quotes:

❌ Invalid:

```bash
'it's broken'
```

✔️ Valid alternatives:

```bash
"it's fine"
'it'"'"'s fine'
```

(Bash closes `'`, inserts `"'"`, reopens `'`)

## Short Answer

> **Wildcard expansion (`*`, `?`, `[]`) only happens on *unquoted* words.**

Double quotes **disable globbing**, even though they allow variable expansion.

---

## The Real Reason (Shell Design Logic)

The shell has **multiple kinds of expansion**, and they don’t all behave the same.

Very roughly (simplified):

1. **Parameter expansion** (`$VAR`)
2. **Command substitution** (`$(...)`)
3. **Arithmetic expansion**
4. **Word splitting**
5. **Filename expansion (globbing)** ← `*`

👉 **Double quotes turn off steps 4 and 5**, but **not step 1**.

---

## Think in Terms of “Intent”

### What does `*.c` mean?

* Unquoted:

  > “Shell, please find matching filenames”

* Quoted:

  > “Shell, I literally want the characters `*`, `.`, `c`”

So:

```bash
echo *.c
```

→ user wants file matching

```bash
echo "*.c"
```

→ user wants the string `*.c`

This is intentional, not accidental.

---

## Concrete Example Walkthrough

Files:

```text
main.c  utils.c
```

### Case 1: Unquoted

```bash
echo *.c
```

Steps:

1. Token: `*.c`
2. Globbing runs
3. Matches filesystem
4. Becomes:

   ```
   echo main.c utils.c
   ```

✔️ Expanded

---

### Case 2: Double-quoted

```bash
echo "*.c"
```

Steps:

1. Token is marked **quoted**
2. Shell says:

   > “This token is protected — do NOT glob”
3. `*` stays literal

Output:

```text
*.c
```

---

## Why Variable Expansion Is Allowed but Globbing Is Not

Because variables are **text substitution**, while globbing is **filesystem lookup**.

Double quotes mean:

> “Replace variables, but treat the result as literal text”

Example:

```bash
DIR=src
echo "$DIR/*.c"
```

Result:

```text
src/*.c
```

If globbing were allowed here, it would:

* Be ambiguous
* Cause unexpected explosions in arguments
* Break scripting guarantees

So the shell enforces:

> **Quoted text never triggers filename expansion**

---

## Key Rule (You’ll Implement This)

When expanding a token:

| Expansion Type | Unquoted | Double-quoted | Single-quoted |
| -------------- | -------- | ------------- | ------------- |
| `$VAR`         | ✅        | ✅             | ❌             |
| Word splitting | ✅        | ❌             | ❌             |
| Globbing (`*`) | ✅        | ❌             | ❌             |

---

## Why This Is Critical for Minishell

When you parse tokens, you must know:

* **Was this character inside quotes?**
* **Which kind of quote?**

So your token data might look like:

```c
struct token {
    char *value;
    bool single_quoted;
    bool double_quoted;
};
```

Then in expansion:

* If `single_quoted` → skip everything
* If `double_quoted` → expand `$`, skip glob
* If unquoted → expand `$` + glob

---

## Mental Model (Lock This In 🔒)

> **Double quotes = “expand variables, freeze the shape”**

They let text change (`$VAR`)
but forbid structure-changing operations (`*`, splitting).

## This Is the Core Rule You’ll Code

> **Globbing happens *after* variable expansion, and only on unquoted text.**

So in minishell logic:

```c
if (token.is_unquoted) {
    expand_vars();
    split_words();
    expand_globs();
} else if (token.is_double_quoted) {
    expand_vars();
    // no split
    // no glob
} else if (token.is_single_quoted) {
    // no expansion at all
}
```
